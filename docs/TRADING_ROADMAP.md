# TRADING_ROADMAP

## 목표

이 앱은 토스증권처럼 쉬운 탐색과 주문 진입을 제공하되, 개인 자동화와 감사 가능한 주문 흐름에 더 강한 매매 워크스테이션을 목표로 한다.

**사용자가 밝힌 목적(2026-08-01)**: 개장 시간에 다른 일을 하고 있어야 해서, **사람이
없어도 도는 자동매매**를 원한다. 여러 에이전트가 서로 검증하며 개선하는 구조를
스킬 하나로 돌리는 것이 그 방식이다.

## ★ A–B 구조 — 에이전트를 매매 경로가 아니라 검증 경로에 둔다

무인 운영과 다중 에이전트 검증을 **한 경로에 섞지 않는다.** 두 축을 가른다.

```
축 A — 운영 (개장 시간, 무인, LLM 없음)
  08:30  오늘의 유니버스 확정   전 종목 스캔 → 그날 볼 종목 목록
  09:00  자동매매 60초 주기     숫자 규칙만. 보유 종목은 항상 포함
  15:30  그날 기록 마감         무엇을 왜 샀고 팔았는지 전부 DB에

축 B — 검증·개선 (사람이 볼 때, 스킬 하나)
  /trading-loop
    data-analyst       그날 실제로 무슨 일이 있었나 (실측)
    market-researcher  외부 사실 — 뉴스·제도·타사
    quant-strategist   왜 그랬나 · 규칙을 바꿔야 하나 (판단)
    trading-dev        바꾸기로 한 것을 구현 + 시험
    (오케스트레이터)    교차 검수 → 사람에게 보고
```

### 왜 가르는가

**축 A에 LLM을 넣으면 셋을 잃는다.**

| 잃는 것 | 왜 |
|------|------|
| 재현성 | 같은 입력에 다른 답이 나올 수 있다. 잃어도 원인을 못 가린다 |
| 백테스트 | "그때 LLM이 뭐라고 했을까"를 과거로 되돌려 잴 수 없다 — **검증 자체가 불가능해진다** |
| 속도 | 수집→분석→판단이 몇 분인데 분봉 전략의 실제 보유 중앙값은 **12분**이다 |

이 레포의 모든 판단은 "재서 정한다"였다. LLM이 판단 경로에 있으면 그 방식이 통하지
않는다.

### **B는 A를 바꿀 수 있다 — 다만 규칙 안에서만** (2026-08-03 결정)

처음에는 "사람이 승인한 것만 반영"으로 정했는데 **목적과 부딪혔다.** 사용자는 개장
시간에 다른 일을 하려고 이 앱을 만든다 — 그런데 승인하려면 사람이 있어야 한다.

그래서 **자동 반영을 허용하되 조건을 건다.** 우려했던 것은 자동 변경 자체가 아니라
**검증 불가능해지는 것**이었고, 그건 조건으로 풀린다.

| 조건 | 왜 |
|------|------|
| **파라미터만. 코드는 못 바꾼다** | 코드가 바뀌면 지금 무엇이 돌고 있는지 알 수 없다 |
| **바꾸기 전에 백테스트를 통과해야 한다** | "재서 정한다"가 이 레포의 방식이다. 못 통과하면 반영하지 않는다 |
| **전부 기록한다** — 언제·무엇을·왜·근거 수치 | 잃었을 때 원인을 찾을 수 있어야 한다 |
| **되돌릴 수 있다** | 직전 설정으로 복귀하는 경로가 있어야 한다 |
| **하루 변경 횟수와 폭에 한도** | 매 회차 바뀌면 무엇이 원인인지 영영 못 가린다 |
| **★ 모의에서만 자동. 실계좌는 승인** | `APP_ENV=prod`면 자동 변경을 끈다 |

마지막이 핵심이다. 모의계좌는 잃어도 가상이라 **실험이 되지만**, 실계좌에서 LLM이
스스로 규칙을 고치면 되돌릴 수 없는 손실이 난다.

**바꿀 수 있는 것과 없는 것을 목록으로 못 박는다** — 목록에 없으면 못 바꾼다.
지금 후보: 전략 선택 · `maxPositions` · `minHoldMinutes` · 후보 선정 문턱.
**리스크 룰과 게이트는 목록에 넣지 않는다** — 그건 안전장치이지 성능 파라미터가 아니다.

### 뉴스를 쓴다면 순서가 있다

뉴스가 주가에 영향을 준다는 것은 맞지만 **그것을 돈이 되는 신호로 바꾸는 것은 별개**다.
전제로 두지 않고 이 순서로 검증한다.

1. **종목 선정을 숫자로 먼저** — 거래대금 급증·등락률·변동성처럼 과거로 백테스트되는 것
2. **뉴스의 값어치를 과거로 잰다** — "뉴스가 난 종목을 그날 샀으면 어땠나".
   우위가 안 나오면 실시간에 넣을 이유가 없다
3. **우위가 확인되면 후보 좁히기에만** — 개장 전 하루 한 번. 매매 판단(언제 사고
   파는지)은 숫자 규칙이 계속 맡는다. 그래야 재현성과 백테스트를 지킨다

순서가 반대면 검증할 방법이 영영 없어진다.

### 켜는 순서 — 무인 운영은 마지막이다

앞의 셋이 안 되면 켜는 것이 손해다. **이길 규칙 없이 무인으로 돌면 그만큼 빨리 잃는다.**

| | 무엇 | 상태 |
|---|------|------|
| 1 | **보유 기간(청산 규칙)을 정한다** | 진행 중(2026-08-01). 청산이 신호 반전뿐이라 종목을 어떻게 고르든 비용에 진다 |
| 2 | 종목 선정을 숫자로 | 지금 240종목(전체 4,041의 6%)이 **종목코드 순**이다 |
| 3 | 모의로 배관 검증 | 3개장일. 손익이 아니라 주문이 실제로 나가는지를 잰다 |
| 4 | 무인 운영 · 뉴스 축 | 위가 다 되고 **이기는 규칙이 확인된 뒤** |

## 토스증권 대비 방향

| 영역 | 토스증권 공개 기능 | 이 앱의 방향 |
|------|------|------|
| 탐색 | 실시간 차트, 주식 골라보기, 인기 종목, 산업/일정/AI 요약 | 관심그룹/추천 리스트/최근 종목을 실시간 시세와 직접 결합 |
| 반복 투자 | 국내·해외 주식모으기, 소수점/금액 주문 | 2단계 이후 `trading_schedules`로 규칙 기반 paper 매수부터 시작 |
| 커뮤니티 | 종목·주제별 커뮤니티, 주주/관심 배지 | 커뮤니티보다 개인 노트·판단 근거·주문 로그 우선 |
| 주문 | 모바일 중심 간편 주문 | 주문 티켓 + 리스크 메시지 + 감사 이벤트를 기본 구조로 강제 |
| 자동화 | 일반 사용자용 일상 투자 루틴 | KIS Open API 기반 개인 전략/자동매매 어댑터로 확장 |

## UI 설계

1. **모니터링 우선**
   - 현재 차트/관심종목 화면을 유지한다.
   - 주문 티켓은 선택 종목 바로 아래에 붙여 차트 맥락을 잃지 않는다.

2. **주문 전 리스크 확인**
   - 매수/매도, 시장가/지정가, DAY/IOC, 수량, 예상 주문액을 한 줄에서 조정한다.
   - 주문 가능 금액, 보유 수량, 1회 주문 한도, 현재가 수신 여부를 즉시 표시한다.
   - 실계좌 전송 전에는 확인 체크와 서버 검증을 모두 통과해야 한다.

3. **감사 가능한 주문 기록**
   - 최근 주문 상태를 티켓 안에 표시한다.
   - 차단 주문도 버리지 않고 `blocked` 상태로 저장해 왜 막혔는지 남긴다.

## DB 설계

현재 구현된 첫 단계 테이블:

- `trading_accounts`: paper/live 계정의 화면용 메타, 주문 가능 금액, 1회 주문 한도, live 잠금 플래그
- `trading_positions`: 계정별 포지션 스냅샷
- `trading_order_intents`: 사용자가 만든 주문 의도와 서버 리스크 검증 결과
- `trading_order_events`: 주문 의도별 상태 이벤트와 payload
- `trading_fills`: paper/live 공통 체결 기록
- `trading_cash_ledger`: 현금 증감 원장

완료된 다음 단계 테이블:

- `trading_broker_orders`: 실주문 전송 시도 기록. 브로커 주문번호·주문채번지점번호·원주문번호와
  차단 사유(`blockers`)를 함께 남긴다. 보내지 못한 시도도 `blocked`로 저장한다.

- `trading_risk_rules`: 계정별 주문 한도(1회·일일), 시장가 허용, 거래 시간대와 개장일,
  종목 허용/차단 목록. 행이 없으면 보수적인 기본값을 쓴다.

- `trading_alert_notices`: 경보를 마지막으로 언제 무슨 내용으로 알렸나. 계좌·경보 종류당
  한 행이고, **같은 경보를 하루에 한 번만 알리게** 하는 기억이다(2026-08-22). 데몬은
  `checkAlerts`를 20분마다 **새 프로세스로** 부르므로 이 기억이 메모리에 있으면 매번
  비어 억제가 걸리지 않는다. 억제되는 것은 알림뿐이고 경보와 종료 코드는 그대로다.

남은 다음 단계 테이블:

- `trading_schedules`: 주식모으기/리밸런싱 같은 반복 주문 규칙

## 구현 순서

1. **완료: paper 주문 기반**
   - 공유 타입 추가
   - DB 스키마 추가
   - `GET /api/trading/overview`
   - `POST /api/trading/orders`
   - 프런트 주문 티켓

2. **완료: paper 체결 엔진**
   - 시장가 paper 주문을 현재가 기준 즉시 체결
   - 포지션/현금 원장 갱신
   - 최근 체결 표시

3. **완료: KIS 계좌 조회**
   - 계좌번호/상품코드는 서버 환경 변수에만 저장하고 프런트에는 마스킹된 계좌명만 전달
   - 국내주식 잔고/평가 스냅샷을 `kis/`에서 `@invest/shared` 타입으로 정규화
   - 종목/가격 기반 매수가능금액(`BrokerOrderability`)을 주문 티켓에 연결.
     실계좌 한도는 paper 주문을 **차단하지 않고** 참고 경고로만 표시한다 (4단계 실주문 게이트의 사전 신호).
   - 체결내역(`BrokerExecutionSnapshot`)을 포트폴리오 감사 기록과 연결.
     미체결·취소·거부도 버리지 않고 같은 목록에 담는다.

4. **진행 중: 실주문 게이트**
   - 완료: 매매 조회 3종 추가 (매도가능수량, 정정취소가능주문, 예약주문 조회)
   - 완료: `POST /api/broker/kis/orders`(현금 매수·매도), `POST /api/broker/kis/orders/amend`(정정·취소)
   - 완료: 게이트 기본 차단. `KIS_LIVE_ORDER_ENABLED=true` + 국내
     주식·ETF·ETN + 수량/단가 검증을 모두 통과해야 전송된다. `GET /api/broker/kis/live-order-gate`가
     막힌 이유를 그대로 알려준다.
   - 완료: 주문 티켓에 실계좌 주문 섹션. paper 경로와 색·영역을 갈라 오발주를 막는다.
     주문 확인 단계를 거쳐야 전송되고, 서버 게이트가 닫혀 있으면 확인 단계까지 가도
     전송 버튼이 잠긴 채로 남는다(2중 차단).
   - 완료: 매도 탭에서 실계좌 매도가능수량 표시 + 초과 시 참고 경고
   - 완료: 미체결 주문 목록과 정정·취소 버튼 (주문 티켓 옆)
   - 완료: 포트폴리오에 실계좌 예약주문 목록
   - 완료: 실주문 전송 시도를 `trading_broker_orders`에 기록. 게이트·검증에 막힌 시도도
     `blocked`로 남고 왜 막혔는지(`blockers`)가 함께 저장된다. 계좌번호·앱키는 담지 않는다.
   - 완료: `trading_risk_rules`로 1회·일일 한도, 시장가 허용, 거래 시간대, 개장일,
     종목 허용/차단을 서버에서 판정. 게이트를 통과해도 룰에 걸리면 KIS에 도달하지 않는다.
   - 완료: 포트폴리오에 리스크 룰 편집 UI. 저장 시 서버가 다시 검증한다
     (1회 한도 > 일일 한도 같은 조합은 저장 자체가 거부된다).
   - **다음: 주문 접수·취소 경로를 사람이 직접 검증** (절차는 `docs/TRADING_API.md` 1번)
   - 완료: 실시간 주문·체결 통보(H0STCNI0) 수신. AES-256-CBC 복호화, 26필드 파싱,
     고객ID·계좌번호는 프런트로 내보내지 않고 화면용 accountId로만 전달.
     `.env`에 `KIS_HTS_ID`를 넣으면 켜진다.

> 매매 API 전체 현황, TR_ID 개편 대응표, 막힌 항목의 이유·해결 방법은 `docs/TRADING_API.md`에 있다.

## 안전 기준

- 기본값은 항상 `paper`다.
- 실주문 코드는 `backend/src/kis/` 밖으로 KIS 원본 필드를 노출하지 않는다.
- 프런트는 계좌번호, app key, app secret, KIS TR_ID를 절대 알지 않는다.
- 실주문 활성화는 환경 변수, DB 플래그, UI 확인, 서버 리스크 검증이 모두 통과해야 한다.

## 전략 성적을 아직 모른다

세 전략의 out-of-sample 성적이 나쁘다고 여러 번 적었는데, 다시 재보니 그건
측정 결과가 아니었다.

KIS 일봉 조회(`FHKST03010100`)는 요청 범위와 무관하게 **100건이 상한**이다
(`days`를 600으로 줘도 100건). 100봉을 70/30으로 나누면 뒤 구간이 30봉인데,
MA(20) 교차는 21봉이 지나야 첫 판단이 선다 — 판단 기회가 9번뿐이다. 거기서
나온 `매매 0회 · 수익률 0%`를 전략 성적으로 읽었던 것이다.

`compareStrategies.ts`는 이제 구간이 `minBars × 3`보다 짧으면 숫자를 내지 않고
`잴 수 없음`이라고 적는다. 지금 조건에서는 뒤 구간이 항상 여기 걸린다.

100일을 넘을 때 KIS가 어느 쪽을 버리는지는 스펙에 없어 추측을 피했다.
삼성전자 100건 → **349건**(2025-02-19 ~ 2026-07-24)이 됐고, 70/30으로 나누면
뒤 구간이 105봉이라 MA(20)의 63봉 기준을 넘는다.

백테스트 전용이다. 종목당 KIS 호출이 최대 5회라 화면 경로에서 쓰면 안 된다.

**뒤 구간(105봉) 수익률**

| 종목 | 이동평균 교차 | 변동성 돌파 | 평균 회귀 |
|------|------|------|------|
| 삼성전자 | +29.03% (2회) | **-31.50%** (17회) | -7.50% (1회) |
| SK하이닉스 | +112.60% (1회) | **-15.70%** (17회) | -9.61% (1회) |
| NAVER | -17.61% (2회) | **-20.74%** (9회) | +39.82% (4회) |

읽을 수 있는 것은 하나뿐이다. **변동성 돌파는 세 종목 모두에서 잃었다.**
매매가 9~17회로 판단할 만한 수이고, 비용이 174,000~326,000원이다 — 전략이
아니라 수수료를 낸 쪽에 가깝다.

이동평균 교차와 평균 회귀는 매매가 1~4회다. 수익률이 +112%든 -17%든 몇 번의
운이지 성적이 아니다. 스크립트가 이제 그런 줄에 `매매가 N회뿐이라 성적이라
부를 수 없다`를 붙인다.

### 8종목으로 표본을 모아 다시 재봤다

한 종목에서 매매가 1~4회라 판정이 안 되니, 뒤 구간 결과를 전략별로 합치는 요약을
넣고 8종목(삼성전자·SK하이닉스·NAVER·현대차·기아·LG화학·셀트리온·카카오)을 돌렸다.
종목별 수익률은 같은 비중으로 평균하고, 매매는 합쳐서 승률을 냈다.

**뒤 구간(각 105봉) 합산**

| 전략 | 평균 수익률 | 플러스 종목 | 매매 합계 | 합산 승률 | 비용 합계 |
|------|------|------|------|------|------|
| 이동평균 교차 | +9.87% | 3/8 | 18회 | 27.78% | 399,563원 |
| 변동성 돌파 | **-13.97%** | **1/8** | **89회** | 31.46% | 1,730,172원 |
| 평균 회귀 | +1.01% | 3/8 | 18회 | 77.78% | 415,005원 |

**변동성 돌파는 확정이다.** 매매 89회는 판정할 만한 표본이고, 8종목 중 1개만
플러스에 평균 -13.97%다. 비용 합계 1,730,172원 — 원금이 종목당 1,000만원이니
비용만으로 상당 부분을 잃었다. 쓰지 말 것.

**이동평균 교차**는 평균이 +9.87%지만 플러스가 3/8이고 승률이 27.78%다. 소수의
큰 수익(SK하이닉스 +112.60%)이 평균을 끌어올린 모양이다. 추세추종의 전형이긴
하지만 매매 18회로는 그게 성질인지 운인지 가릴 수 없다.

**평균 회귀**는 승률 77.78%인데 평균 수익률이 +1.01%다. 자주 조금씩 이기고
드물게 크게 잃는 모양이다 — 승률이 높다는 것만으로 좋은 전략이 아니라는
표본 사례다. 플러스가 3/8인 것도 같은 얘기다.

즉 **셋 중 쓸 만하다고 말할 수 있는 것은 없다.** 하나는 확실히 나쁘고, 둘은
평균이 플러스지만 종목 대다수에서 잃는다. 다음에 볼 것: 종목 수를 더 늘려
이동평균 교차의 매매 표본을 30회 이상으로 만들 것. 파라미터는 그 다음이다.

### 20종목으로 늘리니 판정이 뒤집혔다

8종목 결과를 근거로 `변동성 돌파는 확정으로 나쁘다`를 화면에까지 적었는데,
20종목으로 다시 재니 달랐다.

| 전략 | 8종목 | 20종목 |
|------|------|------|
| 이동평균 교차 | +9.87% · 3/8 · 18회 | +16.84% · 9/20 · 51회 |
| 변동성 돌파 | **-13.97%** · 1/8 · 89회 | **-0.40%** · 8/20 · 215회 |
| 평균 회귀 | +1.01% · 3/8 · 18회 | +2.96% · 11/20 · 40회 |

변동성 돌파의 평균이 -13.97%에서 -0.40%로, 이익 종목이 1/8에서 8/20으로 올라왔다.
8종목이 대표성이 없었던 것이다. 매매 89회라는 표본 크기만 보고 판정을 확정했는데,
**매매 횟수가 많아도 종목 수가 적으면 종목 선택이 결과를 좌우한다**는 걸 놓쳤다.
화면 문구를 `백테스트에서 잃었다` → `백테스트에서 우위 없음`으로 낮췄다.

지금 셋 다 매매 40~215회로 표본 기준(30회)을 넘겼고, 읽으면 이렇다.

- **변동성 돌파** — 215번 사고팔아 비용 460만원을 쓰고 평균 -0.40%. 표본이 가장
  두꺼운데 우위가 없다. 거래를 많이 하는 만큼 비용이 성과를 먹는다.
- **이동평균 교차** — 평균 +16.84%로 가장 높지만 이익 종목이 9/20으로 절반이
  안 된다. 몇 종목의 큰 수익이 평균을 끌어올린 모양이라 아무 종목에나 걸면
  이 평균이 나온다고 볼 수 없다.
- **평균 회귀** — 이익 종목 11/20으로 가장 고르지만 평균이 +2.96%로 작다.
  승률 72.50%에 평균이 이 정도면 이길 때 조금, 질 때 크게 잃는 모양이다.

여전히 "이걸 쓰면 된다"고 말할 수 있는 것은 없다. 다음에 볼 것: 종목별 수익률의
중앙값과 분포(평균만으로는 몇 종목이 끌고 가는지 안 보인다), 그리고 구간을
바꿔 가며 재는 walk-forward.

### 중앙값을 넣으니 순서가 뒤집혔다

평균만 보다 판정을 뒤집은 적이 있어(위 8종목 → 20종목) 합산 요약에 중앙값과
최저·최고를 넣었다. 평균과 중앙값이 5%p 넘게 벌어지면 그 사실을 적는다.

**뒤 구간 105봉 × 20종목**

| 전략 | 평균 | 중앙값 | 플러스 | 최저 | 최고 | 매매 |
|------|------|------|------|------|------|------|
| 이동평균 교차 | +16.84% | **-4.86%** | 9/20 | -31.64% | +223.42% | 51회 |
| 변동성 돌파 | -0.40% | -4.30% | 8/20 | -31.50% | +62.30% | 215회 |
| 평균 회귀 | +2.96% | **+2.21%** | 11/20 | -22.06% | +39.82% | 40회 |

평균만 보면 이동평균 교차가 압도적이다(+16.84%). 중앙값을 보면 -4.86%로 셋 중
가장 나쁘다. 한 종목의 +223.42%가 평균을 혼자 만들었고, 가운데 종목은 잃었다.
평균−중앙값 격차가 21.70%p다.

평균 회귀는 격차가 0.75%p로 셋 중 유일하게 평균과 중앙값이 붙어 있다. 폭은
작지만(+2.21%) 소수 종목이 끌고 간 결과가 아니다.

**보통 종목에 걸었을 때** 순서는 평균 회귀(+2.21%) > 변동성 돌파(-4.30%) ≈
이동평균 교차(-4.86%)다. 평균으로 본 순서와 정반대다.

화면 판정을 이동평균 교차 `unproven` → `no_edge`로 바꿨다. 새로 측정한 게
아니라 같은 데이터에서 중앙값을 본 결과다.

다음: walk-forward(구간을 옮겨 가며 재기). 지금은 한 구간·한 시점이라
2025-02~2026-07이라는 특정 장세에 맞춘 결과일 수 있다.

### 구간을 옮겨 가며 재니 또 달랐다 (walk-forward)

전체 기간(2025-02~2026-07, 349봉)을 셋으로 잘라 각각 따로 쟀다. 이 전략들은
학습하는 파라미터가 없으므로 walk-forward는 "같은 규칙을 서로 다른 기간에
걸어 보고 결과가 유지되는지"를 보는 것이 된다.

**구간별 중앙값 (20종목)**

| 전략 | 1구간 | 2구간 | 3구간 | 매매 합계 |
|------|------|------|------|------|
| 이동평균 교차 | +19.21% (17/20) | +12.27% (14/20) | -4.86% (9/20) | 147회 |
| 변동성 돌파 | -7.90% (6/20) | -1.88% (9/20) | -3.76% (8/20) | 869회 |
| 평균 회귀 | +5.09% (14/20) | +6.14% (18/20) | -2.31% (10/20) | 119회 |

**70/30 out-of-sample은 3구간 하나를 보는 것이었다.** 그 구간이 셋 중 가장
나빴던 탓에, 이동평균 교차를 `no_edge`로 적었던 것은 한 시점만 보고 내린
판정이었다. 앞 두 구간에서는 20종목 중 17개·14개가 이익이었다.
`unproven`으로 되돌리고 문구를 구간별 수치로 다시 썼다.

**변동성 돌파만 세 구간 모두 마이너스다.** 매매 869회로 표본이 가장 두껍고
어느 기간에도 우위가 없었다. `no_edge`는 유지한다.

세 전략 모두 3구간(가장 최근)에서 성적이 나빠졌다. 최근 장세가 이 규칙들에
불리했다는 뜻일 수 있고, 그렇다면 지금 자동매매를 켜는 것은 가장 나쁜
타이밍이다. 다만 구간 셋으로는 그것도 단정할 수 없다.

이 판정을 다섯 번 고쳤다. 순서대로 — ① 측정 불가 구간을 성적으로 읽음
② 8종목으로 확정 ③ 20종목에서 뒤집힘 ④ 중앙값을 넣으니 순서가 반대
⑤ 구간을 나누니 또 다름. 매번 "이번엔 제대로 쟀다"고 적었다는 게 요점이다.

### ⑥ 그 다섯 번이 전부 **러너가 도는 축이 아니었다** (2026-07-31)

위 판정문은 전부 **일봉**으로 잰 것인데 `autoTrader.loadCandles`는
`getInstrumentIntradayCandles`로 **1분봉 120개**를 전략에 넣는다. 같은 8종목·같은
전략을 두 축으로 각각 태우니(비용 포함, 왕복 0.43%) 이렇게 갈렸다.

| 전략 | 축 | 매매 | 승률 | 종목 수익률 중앙값 | 플러스 | 보유 중앙값 |
|------|------|------|------|------|------|------|
| 이동평균 교차 | 일봉 350봉 | 82 | 30.5% | -4.45% | 3/8 | 20일 |
| | **분봉 4거래일** | 242 | **11.6%** | **-11.97%** | **0/8** | **12분** |
| 변동성 돌파 | 일봉 | 351 | 29.1% | -25.75% | 0/8 | 1일 |
| | **분봉** | 1,059 | **6.4%** | **-35.12%** | **0/8** | **1분** |
| 평균 회귀 | 일봉 | 73 | 68.5% | -2.80% | 4/8 | 14일 |
| | **분봉** | 209 | **19.6%** | **-10.00%** | **1/8** | **12분** |

화면(`auto-trader__verdict`)이 자동매매 시작 버튼 옆에 띄우는 문구가
평균 회귀 *"승률 70.8%로 셋 중 압도적 1위"*인데, 러너가 실제로 도는 축에서는
**19.6%**다. 숫자가 낡은 게 아니라 **다른 것을 재고 있다.**

원인은 방향이 아니라 산수다. 분봉 10~20봉 뒤 값 변화 중앙값이 0.34~0.49%인데
왕복 비용은 0.43%로 똑같이 나간다 — 매매의 80~94%가 비용도 못 덮었다.
일봉은 1봉만에 1.005% 움직이므로 같은 비용이 문제가 안 된다.

**이 두 축을 하나로 맞추기 전까지 `verdict`·`backtestNote`는 러너를 판정하는
글이 아니다.** 무엇을 고쳐야 하는지, 반증 조건은 무엇인지, 함께 드러난 러너
결함 4가지(장 마감 청산 없음 · 후보에서 빠진 보유는 못 팖 · 기본 룰이 시장가를
막아 주문 0건 · 분봉 매매량이 일일 20건 한도 초과)는 `docs/USER_FINDINGS.md`
「2026-07-31 장중 — 화면에 뜨는 전략 판정문은 러너가 도는 축에서 잰 것이
아니다」에 있다.

> **고침(2026-08-01) — 축을 맞춘 것이 아니라, 축이 다르다는 사실을 화면이
> 말하게 했다.** `backtestNote` 문장 하나를 `StrategyMeasurement[]`로 바꿨다.
> 축(`CandleAxis`)이 글이 아니라 **필드**이고, 러너 축 측정이 맨 앞에 오며,
> 화면은 위쪽에 `1분봉 · 자동매매가 실제로 보는 봉입니다`, 아래쪽에 `일봉 ·
> 자동매매는 이 봉으로 돌지 않습니다`라고 적는다. 어느 축이 러너의 것인지는
> 서버가 응답에 담아 준다(`StrategyListResponse.runnerAxis`) — 프론트가 박아
> 두면 러너가 축을 바꿨을 때 화면만 조용히 틀린다. 축의 주인은 실제로 분봉을
> 받아 오는 `runCandles.ts`의 `RUNNER_CANDLE_AXIS`다.
>
> **`verdict`는 그대로 두었다.** 분봉 표본이 8종목 × 4거래일로 얇고, 이 레포에서
> 판정은 다시 재서 바꾸는 것이지 새 숫자를 보고 조정하는 것이 아니다. 축이
> 다르다는 사실은 표본과 무관하게 참이라 그것만 화면에 올렸다.
>
> 곁들여 — 전략 목록 조회가 실패하면 드롭다운과 판정문이 함께 사라지는데
> `autoStrategy`는 초기값(`ma_cross`)이라 **시작 버튼이 그대로 눌리고 있었다.**
> 무엇이 걸리는지도 모르는 채 실계좌 매매가 시작된다. 막고 사유를 버튼 옆에
> 적는다. 404를 흉내 내 실제 화면에서 재현하고 고쳤다.
>
> **두 축을 하나로 맞추는 일은 아직 남아 있다.** 분봉 축을 다시 재는 제품
> 스크립트가 없어서(2026-07-31 값은 스크래치패드 도구로 잰 것이다) 그 축의
> 숫자는 갱신되지 않는다. 20종목 × 15거래일 재측정도 그 도구가 있어야 한다.

| 가격 | 1주 값 ≤ 예수금 | 못 사면 후보가 아니다 |
| 유동성 | 하루 거래대금 ≥ 5천만원 | 하루 174주 거래되는 ETF에 주문을 넣으면 호가를 밀고 들어간다. 5천만원은 5만원 주문 하나가 거래대금의 0.1%인 수준 |
| 비용 | 왕복 비용 ≤ 하루 변동폭의 50% | 왕복 비용(수수료 0.015%×2 + 매도세 + 슬리피지 0.1%×2)은 값이 얼마나 움직이든 똑같이 나간다. 하루 0.3% 움직이는 종목은 방향을 맞혀도 진다 |

**왕복 비용은 종목마다 다르다 — 2026-08-12.** 국내 상장 ETF는 매도 거래세가
면제라(종류 무관) **주식 0.43% / ETF 0.23%**이고, 요구 변동폭도 0.860% / 0.460%로
갈린다. 예전에는 한 상수를 모두에게 물려서 그 사이에 있는 ETF가 전부
`costHeavy`로 빠졌다 — 이 계좌의 보유가 전부 ETF인데도 그랬다. 판정은
`shared`의 `krSellTaxRate`가 하고, `screenQuote`/`verdictFor`에 종목을 함께
넘긴다(안 넘기면 예전대로 주식 기준 — 모르는 쪽은 비용이 큰 쪽에 둔다).
`ScreeningResult.thresholds`가 두 값을 모두 담아 화면이 갈라 적는다.

**장 초반 보정.** 유동성 문턱을 하루치로 걸면 09:05에는 전 종목이 걸린다.
지난 장 시간 비율만큼만 요구한다(`sessionElapsedRatio`).

**개장 경계는 초 단위다 — 2026-07-31 장중에 오프바이원을 잡았다.** 예전에는 분
단위로 재고 `분 <= 개장`이라 **09:00:00~09:00:59가 통째로 "장 시작 전"으로
분류돼 비율이 1**이었다. 유효 문턱이 하루치 5천만원이라 개장 첫 1분이
15:29(49,871,795원)보다 엄격했고, 09:01에 128,205원으로 **390배 계단**이 생겼다.
그 1분에 스크리닝이나 후보 선정이 돌면 거의 전 종목을 `illiquid`로 버린다.

| KST | 비율 | 유효 문턱 |
|------|------|------|
| 08:59 | 1 | 50,000,000원 (전일 누적이 이미 하루치다) |
| 09:00:00 | 1/23,400 | 약 2,137원 |
| 09:00:30 | 30/23,400 | 약 64,103원 |
| 09:01:00 | 1/390 | 128,205원 |
| 15:29:00 | 389/390 | 49,871,795원 |
| 15:30:00 | 1 | 50,000,000원 |

분 경계 값은 예전 계약 그대로다(`60k/23400 = k/390`). 마감 쪽(`>= 15:30`)은
실측으로 정상이라 건드리지 않았다.

**비율이 0이 되게 두지 않는다.** `<`로만 고치면 09:00대가 0이 되고 문턱도
0원이라 `turnover < 0`이 언제나 거짓 — **유동성 문이 통째로 사라진다.** 그래서
장이 열려 있으면 최소 1초치는 지난 것으로 본다. 무엇이 걸리는지는 쟀다:
2026-07-31 10:46 실전 서버 `kr-all` 앞 120종목 중 이 문턱 아래인 것은 정확히
**거래대금 0원 6종목**이다(`000880 한화` 등, 현재가는 있고 거래량 0).

**모르는 것은 거르지 않는다. 그러나 0은 아는 값이다** (`knownRangeRate`).
고가·저가를 아직 못 받은 종목은 변동폭 0으로 읽지 않고 비용 문을 건너뛴다.
**고가 = 저가 > 0은 다른 사실이다** — 오늘 한 값에만 체결됐다는 뜻이라 그대로
`costHeavy`다. 예전에는 `if (range > 0)` 하나가 둘을 함께 건너뛰어, **1원 움직인
종목은 버리면서 한 푼도 안 움직인 종목은 통과**시켰다(2026-07-31 실측:
`000227 유유제약2우B`가 09:35·10:00 두 회차 모두 `pass`, 그 사이 거래대금
8,684,600원에서 1원도 안 바뀜). `runScreening`도 같은 함수를 쓴다.

**비용 문턱은 시간비례가 아니다 — 그건 잰 결과다.** 유동성만 `elapsed`를
곱한다. 거래대금은 시간에 쌓이지만 고가−저가는 범위라 같은 방식으로 나눌 수
없어서, 2026-07-31에 과거 3개월(50종목 × 15거래일)의 분봉을 재구성해 쟀다.

| 구간 | elapsed | √elapsed | 실제 폭(중앙값 비) |
|------|------|------|------|
| 09:01 → 09:05 | 5.00배 | 2.24배 | **1.68배** |
| 09:05 → 09:15 | 3.00배 | 1.73배 | **1.27배** |

09:01에 이미 하루치 폭의 25.2%가 벌어져 있다. **시간비례도 √t도 기각됐다.**
다만 지금 잣대가 맞다는 뜻은 아니다 — 초반엔 빡빡하고(09:01 헛탈락 34.7%p)
후반엔 헐겁다(15:00 놓침 50.2%p). 고치려면 "지나간 폭" 대신 "앞으로 남을 폭"을
재야 하고, 그 전에 **보유 기간부터 정해야 한다**(러너는 분봉, 성과 측정은 일봉).
측정 도구와 전체 수치는 `docs/USER_FINDINGS.md`.

**그 "보유 기간부터"를 2026-07-31에 쟀다 — 하루가 아니라 12분이었다.**
분봉 축(8종목 × 4거래일 = 7,238봉)에서 실제 보유 중앙값이 이동평균 교차 12분 ·
변동성 돌파 1분 · 평균 회귀 12분이다. `aheadRangeRate`의 "같은 날 안에 되판다"는
가정조차 실제보다 **26배 긴 지평**을 재고 있었다. 자세한 것은 아래 절.

**걸린 이유를 센다.** 후보가 비면 `거래대금 부족 17종목 · 왕복 비용 초과 2종목`
처럼 어느 문에서 걸렸는지 적는다. `후보 없음`만 쌓이면 문턱을 낮춰야 할지
예수금을 늘려야 할지 알 수 없다.

### 재무 팩터를 어디에 쓸 것인가 — 2026-07-27 실측 후 결정

문턱을 정하기 전에 유니버스의 실제 분포를 쟀다(`financialDistribution.ts`).
통과 28종목 = 주식 14 + ETF·ETN 14, 재무를 받은 주식 12종목:

| 지표 | 최저 | 25% | 중앙 | 75% | 최고 |
|------|------|-----|------|-----|------|
| ROE | -3.28% | 0.00% | **3.64%** | 7.05% | 10.97% |
| 부채비율 | 11.83% | 45.40% | 58.17% | 128.04% | 588.88% |
| 순이익률 | -4.53% | 2.08% | 5.05% | 7.43% | 32.95% |
| 매출성장률 | -7.49% | -2.65% | 3.93% | 8.28% | 23.41% |

**`ROE 10% 이상` 같은 그럴듯한 문턱을 먼저 정했으면 12종목 중 1종목만
남았을 것이다.** 중앙값이 3.64%다. 재 보지 않고 정하면 필터가 유니버스를
비우거나 아무도 안 거른다.

**부채비율 필터는 넣지 않는다.** 588.88%는 한화손해보험이고 보험사는 구조적으로
높다. 하이트진로 190%, DL 148%도 업종 특성이다. 업종 정보 없이 이 지표로
거르면 금융·건설이 통째로 빠진다. 업종 데이터가 생기면 그때 다시 본다.

**재무는 유니버스 필터가 아니라 신호 검증에 쓴다.** 재무 조회는 종목당 KIS
호출 3회다. 후보 24종목을 미리 거르려면 72회가 더 나가는데, 그렇게 해서
걸러지는 건 순손실 1종목뿐이었다. 신호가 난 종목 하나만 확인하면 3회로 끝나고,
그 값이 그대로 "왜 이 종목인지" 근거 기록이 된다.

**ROE 0.00을 조심할 것.** 덕양에너젠·한화손해보험이 ROE 0인데 순이익률은
2.43%·5.09%다. 순이익이 있는데 ROE가 0이면 계산이 안 된 것일 수 있다.
99.99와 달리 0은 진짜 0일 수도 있어 지금은 그대로 둔다 — 판단 근거로 쓸 때
`0이면 모른다`로 볼지 결정해야 한다.
