## 1. 자동감시주문 — 종목별 스탑로스·트레일링 스탑
`자동매매` · 우리 앱 **없음** · 우선순위 **높음** · 시작 전
본 곳: 키움 영웅문 · 한국투자 한투 · NH나무

### 키움이 하는 것
- **보유종목 자동매도**: 스탑로스(이익실현 / 이익보존 / 손실제한), 트레일링 스탑
- **신규종목 자동매수**: 특정가격조건, 저가 트레일링스탑
- **잔고편입 자동매도**: 스탑로스, 트레일링 스탑

감시기준가는 매입단가 / 직접입력 / 감시시작 시점 현재가 / 전일종가 중 선택. 조건 단위는 틱·원·%. 한도 50/50/5개, 유효기간 최대 90일.

### 이게 중요한 이유 — 설계 질문의 답
미뤄 둔 질문이 **"조건을 누가 감시하나"**였는데 키움 도움말이 그대로 답한다:

> 자동감시주문은 HTS, MTS에서 이용할 수 있으며 **HTS, MTS의 ON/OFF 상태에 상관없이** 저장된 감시조건이 만족될 경우 주문조건에 따라 자동으로 주문이 실행됩니다.

**서버가 감시한다.** 우리 러너는 서버 메모리에 살고 재시작하면 멈춘 상태로 시작한다(`docs/ARCHITECTURE.md` — "사람 모르게 되살아나 주문을 내는 쪽이 더 위험하다"는 의도된 결정).

같은 도움말 안에 반례도 있다 — `[0621] 주식StopLoss`는 **HTS를 끄면 자동주문이 수동주문으로 바뀐다.** 같은 회사 안에서도 화면마다 다르니 섞으면 안 된다.

### ⚠️ 전제를 바꾸는 사실 — KIS 오픈API에는 서버측 스탑로스가 없다
공식 레포(`github.com/koreainvestment/open-trading-api`) 전체를 `감시|스탑|트레일링|알림`으로 훑은 결과, 매칭은 **`strategy_builder/` 클라이언트 코드뿐**이다. 한투 HTS `[8251]`의 서버 감시는 **오픈API로 노출되지 않는다.**

`CNDT_PRIC`(조건가격, 스탑지정가호가)이 `order_cash`에 있긴 하다 — 우리는 이미 빈 값으로 보내고 있다. 하지만 **이건 주문 접수 시점의 조건가격이지 지속 감시가 아니다.** 출발점이지 해답이 아니다.

우리가 만들려면 **직접 폴링해서 감시해야 하고**, 그건 위 아키텍처 결정을 뒤집는 일이다.

### 만들기 전에 정해야 할 것
1. **조건을 어디에 저장하나** — 메모리면 재시작에 날아간다. DB에 넣으면 되살아나는데 그건 위 결정과 충돌한다. **사용자가 다시 켜야 도는 쪽**이 이 레포의 기존 판단과 맞는다
2. **발동 시점에 게이트·리스크 룰을 다시 봐야 한다** — 걸어 둘 때 통과했다고 나갈 때도 통과라는 보장이 없다
3. 안 나가는 경우(거래정지·VI·상하한가)를 화면이 미리 말해야 한다

**손절은 위험을 줄이는 동작이라 우선순위를 높음으로 뒀다. 다만 1번이 풀리기 전에는 만들지 않는다.**

## 2. 매도 세율 2026년 인상 반영 (0.18% → 0.20%)
`주문` · 우리 앱 **있음** · 우선순위 **높음** · **완료** (`d62dc6f`)

### 무엇이 문제였나
2026-01-02 양도분부터 코스피·코스닥 매도 세율이 **0.20%**(증권거래세 + 농어촌특별세)인데, 앱은 **0.18%**를 쓰고 있었다. 1월부터 반년 넘게 사용자에게 낼 돈을 적게 말해 왔다.

### 확인
세 출처가 같은 합계를 말했다. 시장별 구성은 출처마다 다르게 적혀 있지만(코스닥을 0.20% 단독으로 보는 곳과 0.05%+0.15%로 보는 곳) **합계는 셋 다 0.20%로 같고, 앱이 쓰는 것은 합계뿐이다.** 코넥스는 인상에서 빠져 0.10% 그대로다.

### 곁가지로 알게 된 것
예전에 백테스트가 0.0018, 수수료 계산기가 0.002를 따로 들고 있어 한 곳으로 모을 때 백테스트 쪽을 골랐는데, **수수료 계산기가 쓰던 0.002가 맞는 값이었다.** 출처 없이 둘 중 하나를 고르면 반은 틀린다.

### 영향
왕복 비용을 구성 요소로 검산: `0.015%×2 + 0.20% + 0.1%×2 = 0.43%` (전 0.41%).
상수 이름의 `ASSUMPTION`도 뗐다 — 이제 출처가 있어 그 이름이 거짓말이 된다.

> **후속(2026-07-29)**: 전략 판정문은 그때 낡았다고 표시만 해 뒀는데, 이후 백테스트의 매수 수수료 누락까지 고치고 다시 재서 갱신했다(`31b6cd2` → `4ff72c5`). 매뉴얼 HTML은 그때 안 따라와 나중에 따로 맞췄다(`c89ed0b`).

## 4. 예약주문에 장전 시간외(05)를 열 수 있다
`주문` · 우리 앱 **일부만** · 우선순위 **보통** · 시작 전
본 곳: 한국투자 한투 · 근거: `backend/src/kis/rest.ts:1514`

### 근거로 확인된 것
`order_resv`의 문서 원문:

> `ord_dvsn_cd (str): [필수] 주문구분코드 (00 : 지정가, 01 : 시장가, 02 : 조건부지정가, 05 : 장전 시간외)`

**예약주문은 `05`(장전 시간외)를 못 박아 허용한다.** 우리는 `'00'`으로 고정하고 있어 이 선택지를 안 쓴다.

### 왜 이것만 되는가
시간외 관련해서 **지금 근거를 갖고 열 수 있는 유일한 문**이다. `06`(장후 시간외)·`07`(시간외 단일가)은 주문 전송 API 문서에 없다 — 그 코드 목록이 나오는 곳은 **매수가능조회**이지 주문 전송이 아니다.

### 열기 전에 확인해야 할 것
예약주문 접수 시각이 출처마다 상충한다 — KIS 문서에 15:10 / 15:40 / 07:00 / 07:30 / 07:50이 섞여 나온다. **실제 접수 시각을 먼저 확인해야 한다.**

## 5. 실현·평가·총손익을 한 화면에서 보여줌
`계좌·손익` · 우리 앱 **일부만** · 우선순위 **보통** · 시작 전
본 곳: 한국투자 한투 · NH나무

### 타사는 어떻게 하나
**한투 [2100] 주식 실시간잔고**가 한 화면에서 명시적으로 갈라 보여준다:
- 실현손익 = 당일매도금액 − 매도분매입금액 − 제비용 (당일 매도분, 실시간 갱신 안 됨)
- 평가손익 = (현재가 − 매입단가) × 수량 − 제비용
- **총손익 = 실현손익 + 평가손익**

**NH [8112] 당일손익평가(체결기준)**도 매매손익(실현)과 잔고평가손익(미실현)을 한 화면에서 분리하고 D+2 정산금액까지 추정해 준다.

### 우리는 둘을 따로 놓고 있다
값은 둘 다 있는데 **서로 다른 카드에 흩어져 있고 합계가 없다.** "내가 오늘 얼마를 벌었나"를 보려면 사용자가 두 카드를 눈으로 더해야 한다.

### 주의 — 성질이 다른 값이다
실현은 **확정된 과거**고 평가는 **아직 안 정해진 현재**다. 합치는 것 자체는 타사도 하지만, **합계만 크게 보이고 구성이 안 보이면 안 된다** — `docs/CODE_STYLE.md`의 "성질이 다른 값은 합치지 말 것"과 부딪히지 않게 하려면 셋을 나란히 보여야 한다.

### 쓸 수 있는데 안 쓰는 API
- `inquire_balance_rlz_pl` — 주식잔고조회_실현손익. docstring: "HTS(eFriend Plus) [0800] 국내 체결기준잔고 화면을 API로 개발한 사항"
- `inquire_period_profit` — 기간별손익 일별합산조회

우린 `inquire_period_trade_profit`(TTTC8715R) 하나만 쓴다. **다만 두 API의 필드를 직접 대조하기 전까지는 어느 쪽이 맞는지 모른다.**

## 6. 호가를 REST 3초 폴링 대신 실시간 WS로
`시세·차트` · 우리 앱 **일부만** · 우선순위 **보통** · 시작 전

### 왜 할 만한가
기능이 늘어나는 게 아니라 **제약이 풀린다.** 지금은 호가를 REST로 3초마다 가져오느라 호출 비용이 종목 수에 비례하고, 그래서 **보고 있는 종목 하나에만** 건다. WS면 그 비용이 사라져 감시목록 전체의 호가를 볼 수 있다.

**이미 깔아 둔 길이다.** `backend/src/kis/realtime.ts`가 체결(`H0STCNT0`)과 주문통보(`H0STCNI0`)를 구독하고 있으니 구독 하나를 더 얹는 것에 가깝다.

### 주의
실시간 구독은 **세션당 종목 수 제한**이 있다(KIS 기본 41개 안팎으로 알려져 있으나 **우리가 잰 값은 아니다**). 체결 구독과 호가 구독이 같은 한도를 나눠 쓰는지부터 확인해야 한다 — 그러면 감시목록이 반으로 준다.

프레임 파서 상수는 TR마다 다르다 — `H0STCNT0`의 `FIELDS_PER_RECORD = 46`을 그대로 또 쓰면 안 된다.

**일등락률 알림** — 전일종가 대비, 종목당 1일 1회, 계좌당 최대 5종목, 가격제한폭(30%) 내

### 우리 앱
**알림이 하나도 없다.** 화면의 `주문 진행 알림`은 이름만 알림이고 실제로는 실시간 체결 통보(`H0STCNI0`) 표시다 — **내가 낸 주문**의 체결이지 가격 도달 알림이 아니다.

### 만들기 전에 정해야 할 것
- **어디로 보내나** — 브라우저 알림은 탭을 닫으면 끝이다. 서버가 보내려면 서버가 계속 켜져 있어야 하고, 그건 자동감시주문과 같은 질문이다
- **호출 비용** — 감시 종목마다 시세가 필요하다. 관심목록 전체에 붙이면 `EGW00201`에 걸린다. 이미 실시간 WS로 받는 종목이 있으면 거기 얹는 쪽이 싸다
- 키움이 **09:00~09:15를 감시 안 하는 것**도 그냥 놓친 게 아니다 — 개장 직후 변동이 커서 알림이 쓸모없어진다는 뜻으로 읽힌다

## 9. 조건검색 — HTS에 저장한 내 조건을 API로 실행

### 왜 우선순위가 낮은가 — 받아적은 전제가 무겁다

> HTS(efriend Plus) [0110] 조건검색 화면에서 조건을 등록하신 후, 왼쪽 하단의 "사용자조건 서버저장" 클릭하셔서 등록한 조건들을 서버로 보낸 후 다시 API 호출 시도 부탁드립니다.
